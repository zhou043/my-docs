## 项目简介

这是课程实践项目的一次完整演练：把平时零散的 Markdown 笔记整理成一个可以公开访问的网站，并且让“更新文档”这件事不再依赖手工操作。

项目比较简单——没有数据库，没有后端服务，也没有前端框架。真正需要维护的只有三样东西：Markdown 源文件、一份站点配置、一条 CI 工作流。

## 技术栈一览

| 工具 | 作用 | 在本项目中的位置 |
| --- | --- | --- |
| Markdown | 编写文档内容 | `docs/*.md` |
| MkDocs | 将 Markdown 构建成静态网站 | `mkdocs.yml` |
| MkDocs Material | 提供主题与界面 | `requirements.txt` |
| GitHub Actions | 自动执行安装、构建和部署 | `.github/workflows/deploy.yml` |
| GitHub Pages | 托管并公开网站 | 仓库 Settings → Pages |

## 一次自动部署的流程

```text
修改 docs/*.md
      ↓  git push
GitHub Actions 触发
      ↓
安装依赖 → mkdocs build --strict → 上传 site/ 产物
      ↓
deploy 任务发布到 GitHub Pages
      ↓
线上网站更新
```

`--strict` 是我加得最值的一个参数：只要站内链接写错，或者导航配置指向了不存在的文件，构建就会直接失败。问题在发布前暴露，而不是等访客点开 404 才发现。

## 实践体会

动手之前，我以为“自动部署”只是把一堆文件传到网上。真正做完之后，收获主要来自三个地方：

1. **配置比想象中重要。** 目录结构、导航入口、仓库的 Pages 权限，任何一处没对齐，流水线都可能以看起来毫不相关的方式失败。排查时按“本地能构建 → Actions 能构建 → Pages 能访问”三段拆开，比盯着报错猜要快得多。
2. **严格模式改变了写作习惯。** 以前写链接随手写，现在每次 `mkdocs build --strict` 都像一次小考，逼着我确认每个相对路径真的存在。
3. **自动化省下的是注意力。** 发布动作本身只要几十秒，但“记得去发布”会一直占着脑子。交给 Actions 之后，我可以只关心内容本身。
