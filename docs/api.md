# API 参考

> 说明：本页接口仅用于演示文档的写法，不对应任何真实服务，示例数据均为虚构。

## 为什么保留一个示例接口

这个项目本身只发布文档，并没有后端。但接口文档是最能体现“结构化描述”的文档类型：同一份信息既要给人读，也要能被工具检查。我借这个示例练习三件事——参数用表格列清楚、示例与说明成对出现、错误情况单独成节。

## 接口一览

| 方法 | 路径 | 功能 | 是否需要鉴权 |
| --- | --- | --- | --- |
| GET | `/api/docs` | 获取文档列表 | 否 |
| GET | `/api/docs/{id}` | 获取单篇文档详情 | 否 |

## 查询文档列表

**请求**

```http
GET /api/docs?page=1&size=20 HTTP/1.1
Host: example.com
Accept: application/json
```

**查询参数**

| 参数 | 类型 | 必填 | 默认值 | 说明 |
| --- | --- | --- | --- | --- |
| `page` | integer | 否 | 1 | 页码，从 1 开始 |
| `size` | integer | 否 | 20 | 每页条数，最大 100 |
| `keyword` | string | 否 | — | 按标题模糊匹配 |

**响应示例**

```json
{
  "page": 1,
  "size": 20,
  "total": 2,
  "items": [
    { "id": 1, "title": "使用指南", "updated_at": "2026-11-02" },
    { "id": 2, "title": "关于本项目", "updated_at": "2026-11-02" }
  ]
}
```

**响应字段**

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `page` | integer | 当前页码 |
| `size` | integer | 每页条数 |
| `total` | integer | 记录总数 |
| `items[].id` | integer | 文档编号 |
| `items[].title` | string | 文档标题 |
| `items[].updated_at` | string | 最后更新日期，格式 `YYYY-MM-DD` |

## 获取单篇文档

```http
GET /api/docs/1 HTTP/1.1
Host: example.com
```

```json
{
  "id": 1,
  "title": "使用指南",
  "content": "本页记录从零开始把这份文档跑起来、改起来、发出去的过程。",
  "updated_at": "2026-11-02"
}
```

文档不存在时返回：

```json
{
  "error": {
    "code": "DOC_NOT_FOUND",
    "message": "指定的文档不存在"
  }
}
```

## 错误码

| HTTP 状态码 | 错误码 | 含义 | 建议处理 |
| --- | --- | --- | --- |
| 400 | `INVALID_PARAMETER` | 参数格式不合法 | 检查 `page`、`size` 的取值 |
| 404 | `DOC_NOT_FOUND` | 文档不存在 | 确认 `id` 是否正确 |
| 500 | `INTERNAL_ERROR` | 服务内部错误 | 稍后重试，并记录请求时间 |

## 写接口文档的体会

写这页时我刻意做了两个调整。

第一，**先写请求和响应，再写解释**。以前我喜欢先大段描述功能，读者要读到最后才知道返回什么。把示例放在前面，正文只补充“示例里看不出来的约束”，比如 `size` 最大 100、日期格式固定。

第二，**错误情况必须单独成节**。只写成功路径的文档，在真正联调时几乎帮不上忙——调用方最想知道的往往是“失败了怎么判断”。把状态码、错误码和处理建议放在同一张表里，比散落在各个接口下面更容易查。

这些写法与[使用指南](guide.md)里的写作约定一致：一页一个主题、能用表格就不用长段落。项目全貌见[关于本项目](about.md)，返回[首页](index.md)。
