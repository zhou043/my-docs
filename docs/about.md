# 关于本项目

## 项目目标

把分散在本地 Markdown 文件里的笔记，变成一个结构清晰、可被公开访问、并且能持续更新的网站。具体拆成三个可验收的目标：

1. **内容与配置分离**：只改 `docs/` 就能更新网站；
2. **构建可重复**：任何人拿到仓库，都能在本地得到同样的站点；
3. **发布无手工步骤**：推送到 `main` 后，线上网站自动更新。

## 为什么选择静态站点

我要发布的是文档，不是应用。没有登录、没有实时数据、没有个性化内容，因此不需要服务器在每次请求时执行代码。静态站点把“生成页面”提前到构建阶段，线上只需要分发文件，速度快、攻击面小，维护成本也低。

真正的难点不在页面本身，而在“改完之后怎么让线上跟着变”。这正是 GitHub Actions 要解决的问题。

## 项目结构

```text
my-docs/
├── docs/                     # 文档源文件
│   ├── index.md              # 首页
│   ├── about.md              # 关于本项目
│   ├── guide.md              # 使用指南
│   └── api.md                # API 参考
├── mkdocs.yml                # 站点配置：站点名、主题、导航
├── requirements.txt          # 构建依赖
├── .github/workflows/
│   └── deploy.yml            # 构建与部署流水线
└── report/                   # 实践报告
```

只有 `docs/` 和 `mkdocs.yml` 会影响网站内容，其余文件服务于构建和记录。把这条边界划清楚之后，日常写作时就不会误改配置。

## 技术选型

| 工具 | 备选方案 | 选择理由 |
| --- | --- | --- |
| MkDocs + Material | Hugo、VitePress | 配置少，Markdown 原生，Material 主题自带导航、搜索和深色模式 |
| GitHub Actions | 本地脚本 + 手动上传 | 与仓库同源，推送即触发，无需额外服务器 |
| GitHub Pages | 对象存储、Vercel | 与仓库权限打通，公开仓库免费，零运维 |

选型时的原则是“够用且少一个活动部件”。每多一个服务，就多一处可能失效的环节，对一次课程实践来说并不划算。

## 设计上的取舍

- **只用相对链接。** 页面之间用 `about.md` 这样的相对路径互相引用，本地预览和线上地址都能正确解析，也方便以后迁移域名。
- **构建即校验。** 在流水线中使用 `--strict`，把链接错误、导航缺失当作构建失败处理，而不是只给一条警告。
- **不引入插件。** 暂时没有搜索之外的强需求，保持依赖最少，构建更快，出错时也更容易定位。

## 我在这件事上学到的

最意外的一点是：自动化的价值不只是省时间，而是把“发布”从一个需要记住的待办，变成一条确定会发生的流程。以前我常在“等有空再整理发布”上拖延；设好触发条件后，文档的更新频率反而稳定了。

另一个体会是关于失败排查的：当流水线报错时，先分清是**构建失败**还是**部署失败**。前者多半是内容或配置问题，本地就能复现；后者通常和仓库权限、Pages 设置有关。把这两类问题分开，排查范围立刻小了一半。
